# Lab 13 - Prometheus and Alertmanager

## Introduction

Prometheus provides monitoring and metric collection, while Alertmanager receives alerts generated by Prometheus and manages their delivery, grouping, silencing, and routing.

The `kube-prometheus-stack` Helm chart already includes Prometheus, Alertmanager, Grafana, kube-state-metrics, and multiple default Kubernetes alerting rules.

In this lab, a custom application-specific alert is created using a Kubernetes `PrometheusRule` resource.

The alert detects when the `container-platform-app` Deployment is scaled to zero replicas.

The complete alert lifecycle is tested:

```text
Inactive
   |
   v
Pending
   |
   v
Firing
   |
   v
Resolved
```

This demonstrates how Kubernetes workloads can be monitored proactively instead of depending only on manual observation.

# Prometheus and Alertmanager

## Prometheus

Prometheus is responsible for:

- Collecting metrics.
- Storing time-series data.
- Executing PromQL queries.
- Evaluating recording rules.
- Evaluating alert rules.
- Sending firing alerts to Alertmanager.

Prometheus determines when an alert condition is true.

---

## Alertmanager

Alertmanager is responsible for:

- Receiving alerts from Prometheus.
- Grouping related alerts.
- Deduplicating repeated alerts.
- Silencing alerts.
- Inhibiting lower-priority alerts.
- Routing notifications to external receivers.

Possible receivers include:

- Email
- Slack
- Microsoft Teams
- PagerDuty
- Webhooks

In this lab, Alertmanager is used to verify that the custom firing alert was received successfully.

---

# Alert Lifecycle

Prometheus alerts move through several states.

## Inactive

The alert expression is false.

Example:

```text
Deployment desired replicas: 2
Alert condition: replicas == 0
Result: false
```

The alert remains inactive.

---

## Pending

The alert expression becomes true, but the configured `for` duration has not completed.

Example:

```yaml
for: 1m
```

Prometheus waits one minute before changing the alert to `Firing`.

This prevents short temporary events from generating unnecessary alerts.

---

## Firing

The condition remains true for the complete `for` duration.

Prometheus changes the alert state to `Firing` and sends it to Alertmanager.

---

## Resolved

The alert expression becomes false again.

Prometheus marks the alert as resolved and Alertmanager removes it from the list of active alerts.

# Step 5 - Create a Custom Prometheus Rule

Instead of relying only on the default Kubernetes alerts, create a custom application alert.

Navigate to the Prometheus Rules directory.

```bash
cd ~/devops_projects_git/homelab-devops/05-container-platform/monitoring/prometheus-rules
```

Create a new rule file.

```bash
nano container-platform-alerts.yaml
```

Add the following configuration.

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule

metadata:
  name: container-platform-alerts
  namespace: monitoring

  labels:
    release: monitoring

spec:
  groups:

  - name: container-platform.rules

    rules:

    - alert: ContainerPlatformDeploymentScaledToZero

      expr: kube_deployment_spec_replicas{namespace="default",deployment="container-platform-app"} == 0

      for: 1m

      labels:
        severity: critical
        application: container-platform-app

      annotations:
        summary: Container Platform Deployment scaled to zero

        description: >
          The container-platform-app Deployment in the default namespace
          has zero desired replicas.
```

Save the file.

Apply the rule.

```bash
kubectl apply -f container-platform-alerts.yaml
```

Expected output:

```text
prometheusrule.monitoring.coreos.com/container-platform-alerts created
```

# How the Alert Works

The custom alert monitors the following Kubernetes metric.

```
kube_deployment_spec_replicas
```

Prometheus continuously evaluates the expression.

```
kube_deployment_spec_replicas{namespace="default",deployment="container-platform-app"} == 0
```

When the Deployment has zero desired replicas:

```
Expression = TRUE
```

Prometheus waits:

```
for: 1m
```

If the condition remains true for one minute:

```
Alert = FIRING
```

If the Deployment is restored:

```
Expression = FALSE
```

The alert automatically returns to the inactive state.

This lifecycle helps eliminate false positives caused by temporary application restarts.

Verify the YAML syntax.

```bash
kubectl apply -f container-platform-alerts.yaml
```

---

Verify that the Deployment has zero desired replicas.

```bash
kubectl get deployment container-platform-app
```

```
kube_deployment_spec_replicas
```

---

## Alert Does Not Reach Alertmanager

Verify Alertmanager is running.

```bash
kubectl get pods -n monitoring
```

Verify the Prometheus Alertmanager configuration.

---

## Alert Remains Firing

Verify the Deployment has been restored.

```bash
kubectl get deployment

kubectl get pods
```

Wait until Prometheus evaluates the rule again.

# Conclusion

In this lab, a custom Prometheus alert was created to monitor the `container-platform-app` Deployment running in Amazon EKS.

A `PrometheusRule` resource was deployed to evaluate the number of desired Deployment replicas using the `kube_deployment_spec_replicas` metric exposed by `kube-state-metrics`.

The application was intentionally scaled to zero replicas, causing the alert condition to become true. After the configured evaluation period, Prometheus transitioned the alert from **Pending** to **Firing** and forwarded it to Alertmanager.

Alertmanager successfully received and displayed the alert, demonstrating the complete monitoring pipeline.

Finally, the Deployment was restored to two replicas, returning the alert to the **Inactive** state and completing the full alert lifecycle.

This lab demonstrates how Prometheus and Alertmanager can be used together to proactively detect and manage application failures in Kubernetes environments.
